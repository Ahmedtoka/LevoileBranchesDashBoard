# Observations Module — Plan H: Manager approval gate + simple department reply (demo flow, owner request 2026-10-25)

> For agentic workers: use superpowers:executing-plans (TDD per task, commit per task). Two parts run in parallel: **H-backend** (worktree `wt-approval`, branch `feat/observations-approval`) and **H-mobile** (`BranchesMobileApp`, branch `feat/observations`). Contract below is fixed; both sides code against it.

**Goal (the owner's demo flow, verbatim intent):**
1. Employee (mobile): types first 3 letters of a branch ("maa") → branch cards → card shows branch name with **Check-in** and **Start** → visit screen with **two tabs**: "من الكتالوج" (per-department list) and "كتابة تعليقات" (free).
2. Free tab: a text input + "إضافة نقطة جديدة" button; each point row has an optional **priority box**, a **photo button**, and a **department button** (to direct the note to a department). No AI required here.
3. When the employee closes the free tab → a **review list** of everything entered → "اعتماد وإرسال". **This does NOT create tickets.** The visit becomes `submitted` = awaiting the reporting department's manager.
4. Department manager (mobile or web): sees submitted visits of their department, opens one, sees all points, presses **"فحص"** → the AI assigns responsible department + risk for every point automatically; the manager eyeballs/edits, then **"اعتماد الزيارة"** → now each point becomes a ticket in its responsible department.
5. Responsible department: sees only its points (tickets) and replies with one of two buttons: **"جاري العمل عليها"** or **"تم الحل"**, each with a **mandatory note** (photo optional on "تم الحل").

## Contract (API, under `auth:sanctum`, same conventions as Plan B)

- `observation_visits.status`: `draft` → `submitted` (awaiting approval; **no tickets**) → `approved` (tickets created) ; `rejected` optional (not needed now). Add `approved_by`, `approved_at` (guarded migration). Existing `submitted` rows from import/demo keep tickets (one-time: the migration sets `status='approved'` where `submitted_at` is not null and the visit has at least one ticket).
- `POST /observation-visits/{id}/submit` → marks `submitted`, notifies the manager(s) of the reporting department (`notifications` type `observation_visit_submitted`), **creates no tickets**. Response `{visit}`. (Behind config `observations.manager_approval` default `true`; when false the old behaviour.)
- `GET /observation-visits?status=submitted&scope=to_approve` → visits of the user's reporting department(s) awaiting approval (department managers, ops, super). Each item adds `pending_points`.
- `POST /observation-visits/{id}/classify` (manager only) → runs the classifier on **every observation of the visit that has no catalog item** (uses the existing `ai-check` machinery with the saved descriptions), writes `responsible_department_id`, `risk_level_id`, `category_id` suggestions directly onto those observations (keeps `classification_status='ai_pending_review'`, records `ai_classifications` rows with `observation_id`), returns `{status, observations:[...]}` (full observation objects). Failure → `{status:'failed', message}` and nothing changes.
- `PUT /observations/{id}` (manager of reporting dept, ops, super; visit not yet approved) body `{responsible_department_id?, risk_level_slug?, category_id?, description?, kind?}` → updates; returns `{observation}`.
- `POST /observation-visits/{id}/approve` (manager only) → for every `kind=issue` observation creates the ticket exactly as the old submit did (same `ObservationService::ticketAttributesFor`), requires `responsible_department_id` on every issue (422 listing the ones missing), sets visit `approved`, `approved_by/at`, notifies responsible department managers. Response `{visit, created_tickets:[...]}`. Idempotent.
- Employee free points may carry optional `responsible_department_id` and `risk_level_slug` at upsert time (already supported); when the employee sets nothing, the point is saved with `category_id = <department's "other" category>`, `kind='issue'`, risk null, responsible null.
- `POST /tickets/{id}/reply` body `{state: 'working'|'solved', note (required, min 3), photo_path?}` for users of the ticket's department (manager or employee): `working` → assigns to the actor if unassigned and moves the ticket through `assigned → on_the_way → in_progress` in one call (log rows with the note); `solved` → same chain then `waiting_approval`, with `photo_path` recorded as `after` evidence when given (so the approver can close). Response `{ticket}`. The existing fine-grained endpoints stay.
- Observation objects gain `visit_status` and `can_edit_classification` (bool for the current user).
